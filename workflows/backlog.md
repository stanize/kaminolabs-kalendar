# Backlog

Nice-to-have features or improvements that are real candidates eventually,
but not committed to or scoped yet. A short bullet with a one-line

- **Admin-portal tool: merge a WhatsApp guest client record into a patient portal account** (2026-09-22, Arun, low priority). Once WhatsApp guest bookings dedupe by phone (see `workflows/whatsapp-booking.md`), a patient who also has a real portal account ends up with two separate `kalendar_clients` rows for the same business — one linked via `patient_id` (portal), one matched via phone (WhatsApp). Arun's call: not worth building live self-service verification (discussed: a WhatsApp-reply-based one-time code is the sound approach if this ever gets built — proves phone ownership without any OTP/SMS infra or Meta template-approval friction, since it's just a normal inbound reply — but a plain "send an unsolicited code to a typed number" OTP flow is NOT the right shape, ruled out during discussion). For now, handle it manually via `kaminolabs-kalendar-admin` — an admin tool that lets Arun pick two `kalendar_clients` rows for the same business and merge them (re-point bookings/counters from one onto the other, delete the duplicate). Not scoped or started.
- **Natural-language WhatsApp booking parser (free-text intent parsing via an LLM, e.g. Gemini)** (2026-09-23, Arun, deferred — revisit if the client asks). A client-supplied spec proposed adding a free-text NLP layer in front of the existing menu/list-driven WhatsApp bot — patient types a full sentence ("book a dental checkup next Friday at 10am"), an LLM extracts structured booking parameters to pre-fill the flow, falling back to the normal tap-menu on low confidence. Arun agreed to defer after discussion; reasons on record for when this gets revisited:
  - **Reverses an already-settled non-goal.** `workflows/whatsapp-booking.md`'s original design explicitly ruled out free-text NLP ("list/button taps only") — this isn't a small addition, it's undoing that call, so revisiting it should be deliberate, not incidental.
  - **Free-tier data-use is a real compliance risk, not a technicality**, for a healthcare-adjacent product under GDPR: Google's Gemini **free tier** allows Google to use submitted data to improve their products (the paid tier doesn't). The spec's proposed local regex-based PHI redaction (scrubbing names/phones before the API call) is inherently unreliable — regex name detection misses real-world input constantly — so "sanitized" text sent to a free-tier model is a soft promise, not a guarantee. If this is ever built, it should be on the **paid** tier from day one, not free.
  - **Marginal value vs. real added complexity**: the current flow is already just 4 taps (service → date → time → confirm). Free-text parsing saves a few seconds of tapping in exchange for a new external API dependency, new latency/timeout/rate-limit failure modes, and a new secret/config question (global platform key vs. per-clinic — the same unresolved shape the Twilio credential design had to work through).
  - **Spec was written generically**, not against this repo's actual stack (proposed Python + `google-genai`; this is a Next.js/TypeScript codebase — a JS/TS Gemini SDK exists, so this is fixable, but it confirms the spec wasn't checked against real code, same pattern as the original WhatsApp spec needing correction).
  - Plan: Arun is sharing the current tap-based flow with the client first to gauge real demand before any of this gets revisited.
