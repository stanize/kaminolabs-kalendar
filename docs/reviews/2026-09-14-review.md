# Kalendar — Go-Live Readiness Review
**Date:** 2026-09-14
**Compared against:** `docs/reviews/2026-07-26-review.md`

## 1. Bottom line

A lot has shipped since July 26 — payment collection (Stripe SaaS billing) went from "doesn't exist" to fully built and webhook-synced, plus a substantial bono/session-package system and a guest/patient unification pass. The core booking loop (public booking → confirm → reminders → clinic follow-up) is genuinely solid engineering. But for onboarding a real clinic specifically, the gap isn't feature completeness anymore — it's operational safety net: there's no privacy policy/terms of service anywhere in the repo (this handles health-adjacent patient data under GDPR), no spam/bot protection on the public booking form, and no real error monitoring (the team explicitly deferred Sentry until "real traffic/paying clinics" — which is now). None of these are big builds, but shipping without them for a live clinic is the actual risk, not a missing feature.

## 2. Since the last review

| Item (from July 26) | Status | What changed |
|---|---|---|
| Payment infrastructure | **Done** | Full Stripe subscription billing — customer/subscription creation, webhooks, discount-phase pricing, in-app Elements modals, billing portal fallback. Well beyond "spec exists" now. |
| Patient portal: self-service actions | **Partial** | Guest/patient unification shipped (claim history across businesses on verification) — but still no self-service cancel/reschedule from the portal itself. |
| Basic owner analytics | **Not started** | No booking-volume/no-show-rate reporting found anywhere. Flagged two reviews running now. |

Not in the last review's recommendations but shipped anyway: a full **bono (session package) system** — types, purchase recording, atomic DB-trigger-based session deduction, usage reporting, reversal — and a **guest-immediate-confirm** redesign that dropped the old 24h pending/expiry window entirely.

## 3. What's genuinely strong

- **The Stripe billing build is careful, not rushed** — idempotent webhook processing via `kalendar_stripe_webhook_events`, price computed server-side and locked at subscription-creation time (never trusts Stripe as price source of truth), and real production issues (missing `confirmation_secret` expansion, Bitwarden blocking `js.stripe.com`) were caught and fixed with actual fallback paths, not just patched over.
- **The bono session-deduction moved from app code to a DB trigger** (`sync_bono_session_usage`) — correct instinct, removes a class of race-condition bugs from app-layer accounting.
- **The immediate-confirm redesign is a real UX improvement** — no more 24h limbo for guests, with `clinic_reviewed_at` as a clean follow-up flag layered on top rather than conflated with booking status.

## 4. Gaps that block a safe go-live — ranked

1. **No privacy policy / terms of service in the repo.** This product now handles physiotherapy patient data (health-adjacent) under Spanish/EU GDPR — this was flagged as a blind spot in the last two reviews and still hasn't moved. This is the single item I'd treat as a hard blocker before a real clinic sends real patients through the booking flow.
2. **No spam/abuse protection on the public booking wizard** — no captcha, honeypot, or rate limiting anywhere in `submitBooking`. A public form that now (since Sept) confirms bookings immediately with no review window is more exposed to junk/abuse than the old pending-confirmation version was.
3. **No real error monitoring.** `log-client-error` explicitly says Sentry was deferred until "real traffic/paying clinics" — that condition is about to be met. Right now a silent failure (a reminder that doesn't send, a webhook that doesn't process) is only visible if someone happens to check Vercel logs.
4. **No backup/data-safety story documented** — Supabase almost certainly has PITR available on the plan, but nothing in the repo confirms it's configured or tested for this project specifically.

## 5. Blind spots not currently tracked

- **What a clinic owner sees when something silently fails** — reminder failures have a UI marker now, but Stripe webhook failures, email-send failures on booking confirmation, and bono-trigger failures have no owner-facing surface.
- **Support/incident contact for a paying clinic** — the support ticket form exists for Arun to see tickets, but there's nothing for "the booking page is down" urgency.

## 6. Technical risk with business consequences

- The public booking form's lack of any abuse gate is the one worth losing sleep over with a real clinic live — a scraped/spammed slug gets junk bookings mixed with real patient data immediately, no review step to catch it.
- Everything else (payments, bonos, reminders) is built with enough defensive idempotency that there's no obvious revenue-losing failure mode there.

## 7. Recommended next 3

1. **Privacy policy + basic terms of service**, published and linked from the public booking page — this is the item that's actually gating "can this ethically go live with a real patient," not a nice-to-have.
2. **Basic bot protection on the booking wizard** (a honeypot field is a cheap first pass; Turnstile if junk actually shows up) — cheap, and now more urgent since there's no confirmation-review window to catch abuse downstream.
3. **Wire up Sentry** (or even just a scheduled digest of the `log-client-error` console logs) before the first real clinic goes live, not after — better to know about a broken webhook before the clinic reports it.
