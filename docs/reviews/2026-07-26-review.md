# Kalendar — Product Review
**Date:** 2026-07-26
**Compared against:** `docs/reviews/2026-07-18-review.md`

## 1. Bottom line

Reminders — the flagship feature from the last review — is genuinely shipped, and shipped better than the spec asked for: they moved the scheduler to Supabase `pg_cron` after real GitHub Actions run data showed 1h50m–3h11m of jitter, which is exactly the kind of "notice it in production, fix it before it matters" judgment that matters at this stage. The failure-visibility item was built alongside rather than deferred, as recommended. That's the single biggest gap from last time closed cleanly. The other flagged gap — payment collection — is still fully unaddressed in code, though a pricing/discount spec document now exists, which reads as "designed, not yet built." The team is moving fast and shipping well; the risk is narrowing scope discipline as more ideas (patient portal expansion, pricing) stack up before the payment gap closes.

## 2. Since the last review

- **Shipped:** Appointment reminders (24h/1h), including owner-facing failure visibility (`reminder_send_failed`, `last_reminder_error` surfaced via `lib/booking/owner-data.ts`) — both recommended items from last review, done in the same change rather than split.
- **Shipped:** Reminder scheduling moved from GitHub Actions to Supabase `pg_cron` + `pg_net` after observing real scheduler jitter — a good example of validating against production behavior rather than assumptions.
- **Shipped:** Client-facing email redesign — business branding, icon rows, manage-appointment button.
- **New but not yet built:** A pricing/discounts spec document (`docs/specs/pricing-and-discounts-spec.md`) — this is planning, not implementation. Payment collection itself (Stripe, plan gating) is still entirely absent from the codebase, same as last review.
- **Unchanged:** No analytics/reporting for owners. No GDPR/privacy-policy artifacts found. No referral/word-of-mouth mechanism.

## 3. What's genuinely strong (new since last time)

- **The pg_cron pivot is a strong signal of engineering maturity** — noticing that GitHub Actions' shared scheduler queue can't hold a ±15-minute window reliably, and moving the timing-critical piece into Supabase's own Postgres instance instead, is the right fix and was caught before it caused a customer-visible miss.
- **`EMAIL_LOCALE` pin** (defaulting all guest emails to Spanish until `business.language` exists, while leaving `guest_locale` untouched for on-page UI) is a pragmatic call — it avoids half-translated production emails without blocking on a field that doesn't exist yet.
- **Idempotency discipline held up under a second feature** — the reminder columns follow the exact same nullable-timestamp pattern as `pending_expiry_at`, and the manual GitHub Actions fallback is explicitly designed to never double-send even if run concurrently with pg_cron.

## 4. Gaps that block revenue or retention (ranked — carried forward + updated)

1. **Payment collection still doesn't exist.** This was #1 last review and remains the largest gap to €1M ARR. A pricing/discounts *spec* now exists, which is good progress on design, but there is still no Stripe integration, no plan/tier table, and nothing that bills anyone. Recommend this becomes the very next build after any in-flight work, before further scope (patient portal expansion, below) gets added on top.
2. **No analytics/reporting for the owner** — unchanged from last review. Still no booking-volume, no-show-rate, or revenue-adjacent numbers for an owner to point to when deciding whether to keep paying (once there's something to pay for).
3. **GDPR/privacy posture still not visible in the repo** — unchanged. Matters more, not less, now that the product has more sensitive touchpoints (patient portal, reminders with appointment content in emails).

## 5. On the patient-portal expansion idea

Worth flagging before scoping new work: **a patient portal already exists** and is functional today — login (Google + email/password), a dashboard, and a bookings list (upcoming + past) at `app/patient/(protected)/`. It's tagged `⚠️ WORK IN PROGRESS` in `MODULES.md` specifically because a new component (`patient-auth-card.tsx`) landed without a dedicated resync yet, not because the core flow is missing.

What it does **not** yet do, which is likely what "see their appointments, etc." is reaching for:
- **No self-service cancel or reschedule from inside the portal** — the bookings list is read-only (status badges only); a patient today would need to use the email cancel link, not the portal itself.
- **No profile/contact-info editing** (phone, name) from the portal.
- **No booking-from-the-portal shortcut** ("book again with the same provider") — every new booking still starts from the public `/bookings/[slug]` page even for an already-logged-in patient.

Recommend treating this as **portal feature expansion**, not a new site — the auth, role model (`user_roles`, `kalendar_patients`), and route structure are already in place, so a new project scope doc should be about which of the three gaps above to close first, not about auth/data-model groundwork. It'd also be worth folding in a resync of the existing WIP tag while you're in that code either way, since the module's already flagged as needing one.

## 6. Recommended next 3

1. **Payment infrastructure** — carried forward, now overdue relative to reminders being done. The pricing/discounts spec is a good head start; the next step is turning it into an actual Stripe/plan-gating build.
2. **Patient portal: self-service cancel (and later reschedule once rescheduling itself ships)** — the highest-leverage single addition to the existing portal, since "see my appointments" without "do anything about them" is a half-finished loop for the patient.
3. **Basic owner analytics (booking volume, no-show rate)** — still unaddressed, and becomes more urgent once there's a subscription to justify.
