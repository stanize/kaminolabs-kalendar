## 3. What's genuinely strong

- **The logging convention is a durable asset, not a one-off.** `logEvent()` is written into `CLAUDE.md` as a standing rule, severities double as a debug log, and errors carry stable codes. Write-side liveness was proven against a real production `pg_cron` run, not assumed. The "confirm live via read-only query" discipline is also what caught the last review's migration ambiguity.
- **The testing-tracker is the right answer to a recurring weakness.** The same finding has surfaced in three reviews: code merged, never exercised. A repeatable, categorized regression checklist addresses that class of problem directly. It only pays off if it gets used.
- **Failure direction remains sound.** Rate limiting fails open, `logEvent` is additive to `console.*`, and reconcile logs mismatches instead of auto-correcting.
- **Cancel, bonos, reminders and the booking flow remain solid.** Nothing regressed in these areas.

## 4. Gaps that block revenue or retention — ranked by impact vs. effort

1. **Live-test the holidays engine and the rate limit against real data.** Effort: a few hours of Arun's time. Seven `in_progress` steps are sitting on schema confirmation alone. The failure mode is patient-facing: a closed slot that shows as bookable, or the reverse. *Matters for €1M ARR: a failed first demo costs more than the hours to prevent it. The testing-tracker now exists to run exactly this.*
2. **Commission the GDPR legal review.** Effort: a phone call or email, then external lead time. The public privacy page is a placeholder while the product handles physiotherapy patient data. *Matters: this is the one hard go-live blocker engineering cannot shorten, and every week of delay is a week before the first real clinic can launch.*
3. **Owner analytics.** Effort: moderate (booking volume, no-show rate, bono usage, cancellations). *Matters: the pitch is "cut no-shows", yet `no_show` status is recorded per booking while the owner has no view of the trend. A clinic that can't see the value is a clinic that cancels at month 7, which is right when the free 6-month window ends.*
4. **No-show reduction is reminders-only.** `/panel/payments` is confirmed placeholder debris, and there is no deposit, prepayment or no-show charge anywhere in the code. The only Stripe flow bills the clinic (`lib/actions/billing.ts`). The pitch includes "payment collection". *Matters: that is a pitch-versus-product gap. Reminders do reduce no-shows, but the stronger lever isn't built, and neither is the part competitors win deals on.*
5. **The free-period expiry is a cliff with nothing behind it.** Subscription gating is deferred by decision and the 6-month free offer is deliberate. Fine for MVP, but billing-failure banner, feature-gating and trial mechanics are all `deferred`. *Matters: the first cohort converts to paying roughly six months after launch, and nothing yet exists to convert them.* Not urgent today, but it needs a dated trigger rather than an open-ended deferral.
6. **No patient self-reschedule.** *Matters: patients who can't reschedule either cancel and lose the slot or call the clinic, which is the admin work the product promises to remove.*

## 5. Blind spots not currently tracked

- **Staging versus production isolation.** All verification so far has been against the single live Supabase project `rlxfcmijbesoblissmtd` (the migration check, the schema reset admin feature, test patient provisioning at `/api/internal/provision-test-patients`). Nothing in the repo describes a staging environment. Test data and real patient data will share one database once the first clinic goes live.
- **Dev-phase destructive tooling in the production surface.** `/api/internal/schema` (serves schema SQL for an admin reset feature, flagged "temporary"), plus the destructive-reset path and test-data provisioners. The planned audit should cover these, but nothing records a retirement date or a guard against running them post-launch.
- **Process drift in the tracker itself.** Seven workflow steps are `in_progress` pending live testing, so a `Status:` line can't be trusted at a glance. Add a "live-verified date" per step, or the next review will re-derive this from commit messages again.
- **Reviewing the review's own cadence.** This session landed four days after the last one, with 15 commits and almost no product change. A review is most useful when product has moved. Consider gating on shipped user-facing steps, not just commit count.
- **Mobile.** Still no tracking or "we checked, it's fine" note anywhere, as of this review. Owner analytics and the calendar are the likeliest places a solo practitioner on a phone gets stuck.
- **Multi-provider/multi-location.** Holidays introduced per-provider concepts, but nothing tracks the broader scaling story.

## 6. Technical risk with business consequences

- **Unexercised code is still the dominant risk.** The holidays availability engine and the rate-limit path are both live-schema but never driven end-to-end. The new logging only helps if someone reads the dashboard, and the read side itself is unverified.
- **Logging is now a second write path in hot code.** `logEvent` calls sit in `submitBooking`, webhooks and crons. Confirm it is truly fire-and-forget and cannot throw or add latency into the booking path, and that a failing `kalendar_error_log` insert degrades silently. Not verified in code during this review. It's worth one targeted check, since a logging helper breaking a booking would be a self-inflicted outage.
- **Unrun migrations pending.** `schema_subset_018` (error code column) is unconfirmed live. `019`–`021` (customer dashboard, testing tracker) should be checked too. A deploy ahead of its migration makes the matching admin query fail.
- **Single database, single Hobby-plan Vercel project, no PITR note.** A bad migration or a mistaken `DELETE` has no documented recovery path.
- **Payments/bonos side remains as solid as before.** No new risk there.

## 7. My recommended next 3

1. **Run the testing-tracker against holidays and rate-limiting this week, before any demo or launch.** It is the most direct use of the tool just built, and it closes the longest-running "built, never exercised" finding. Also open `/admin/error-log` once and confirm `schema_subset_018` ran.
2. **Commission the GDPR privacy and ToS review now, outside any engineering work.** It is the only hard blocker with external lead time, and it has now been flagged four reviews running. The shell, routes and links are done, so this is a content swap once text exists.
3. **Build minimal owner analytics: bookings per week, no-show/cancel rate, bono usage.** It is the cheapest feature that proves the core pitch to the buyer, and it is the retention lever for the end of the free period.

Carried forward but not in the top 3: confirm a PITR/backup plan and run the security/performance audit before launch. Both are cheap relative to the cost of the failure they prevent.
